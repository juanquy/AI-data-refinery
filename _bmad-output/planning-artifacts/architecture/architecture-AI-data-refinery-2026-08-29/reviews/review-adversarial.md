# Adversarial Review — Architecture Spine, AI-data-refinery

**Method.** For each candidate hole I constructed two feature-level units (from the PRD's launch surface: corpus+verticals, on-demand refinement, MCP, REST/OpenAPI, search, custom schemas, pipelines, webhooks, Stripe+quotas, agent rails, marketplace, export, Studio, SDKs, ops console) and attempted two builds that each satisfy every AD verbatim yet cannot integrate — clashing shared-data shapes, two owners of one entity, or conflicting money/state paths. Only pairs where the spine's own text demonstrably permits both builds are reported. Candidates the spine already closes were discarded (examples at the end).

**Severity scale.** CRITICAL = incompatible data/money shapes or two owners of one entity; HIGH = rework-forcing divergence; MEDIUM = friction.

---

## CRITICAL findings

### C1. The custom-schema document itself has no pinned representation — six units each get to invent one

- **Units:** Studio schema builder (FR-040/041) × refinement validate filter (AD-9) — and transitively MCP tool provisioning (FR-042), REST/OpenAPI, marketplace blueprints (FR-043), export.
- **Incompatible-but-compliant builds:** The Studio team stores schemas as JSON Schema draft 2020-12 documents (natural for a no-code builder with raw-JSON expert mode, and what MCP tool `inputSchema` requires on the wire). The refinement team expects a Zod-serializable definition (natural in a codebase whose validation religion is Zod per AD-5/AD-8/AD-9) and validates with Zod semantics. These disagree on `additionalProperties` defaults, coercion, union semantics, and format handling — the same extraction can pass one and fail the other, which per AD-9 is the difference between a served result and a quarantined, non-billable failed run. Marketplace blueprint cloning and FR-042's "live preview of the MCP tool definition" each need whichever format their neighbor didn't pick.
- **Spine text that permits both:** AD-5 pins only compile-time tables: "Tables are defined once as Drizzle schema in `packages/schema`" — tenant schemas are runtime *data*, not tables. AD-9 demands only that "every extraction path names a real one" without naming a schema language or validation dialect. The capability map's "Custom schemas | `core/corpus` + `packages/schema` runtime defs" names a location, not a format or semantics.
- **Why critical:** the custom schema is the single most-shared data shape in the product (Studio ↔ refinement ↔ MCP ↔ REST ↔ marketplace ↔ export all consume it), and validation-semantics drift changes billing outcomes (AD-11 bills only delivered results). FR-021's "domain-aware rules" for diff severity also need a home on this artifact and currently have none.
- **Tightening:** New AD (or AD-5 extension): tenant/custom schemas are stored as a single canonical format (name it — e.g., a constrained JSON Schema profile defined in `packages/schema`, with the allowed keyword subset enumerated), validated at publish time against a meta-schema; exactly one compiler in `packages/schema` maps it to (a) the runtime validator used by the validate filter, (b) the MCP tool inputSchema, (c) OpenAPI component schemas. Diff-severity rules attach to the schema document in a named field. Any second parser/compiler of schema documents is a defect.

### C2. AD-11 makes invoicing and creator attribution "reads of the ledger" without pinning what a ledger row must carry

- **Units:** metering/Stripe invoicing × marketplace accrual (FR-081/082).
- **Incompatible-but-compliant builds:** Build A stamps each `usage_events` row at serve time with the unit price (micro-USD) and, where the serve went through a marketplace listing, the `lst_` reference and the 80/20 split basis — attribution is point-in-time. Build B stores only `{unit type, principal}` (the only attributes AD-11 names) and computes revenue and creator share at read time by joining current pricing config (founder-editable, FR-074) and current listing state. The two produce different money whenever a price changes, a listing is created/retired after the fact, or a creator changes a listing price (FR-083) — and FR-081 ("computed per query on revenue actually collected") is satisfiable under either reading. Reconciliation (FR-065) between a Build-A ledger and Build-B invoicing never balances.
- **Spine text that permits both:** AD-11 pins the row as "one row in append-only `usage_events` … attributed by principal (workspace/key/agent-token, or x402 payment reference)" — principal attribution only, no price field, no listing/creator field — and then asserts "Quotas, 402 responses, Stripe invoicing, x402 settlement, and marketplace attribution are all *reads* of this ledger," which is only realizable if the row carries content no AD requires it to carry.
- **Tightening:** Extend AD-11 with the minimal row contract: every `usage_events` row carries unit type, principal attribution, **priced amount in micro-USD frozen at serve time**, pricing-config version, and (when the serve is grant-mediated) the `lst_` listing reference and split basis. Ledger reads never join mutable config to compute historical money; compensating events are the only way past money changes.

### C3. Nobody owns the cached_read-vs-refinement classification or the definition of one "billable act"

- **Units:** corpus/search serving × on-demand refinement (and metering, which writes what it's told).
- **Incompatible-but-compliant builds:** (1) A `refine` request for a URL+schema whose fresh result sits in KV: the corpus team serves the cache and classifies `cached_read`; the refinement team, receiving the same request on the MCP tool, honors the verb and runs a fresh extraction billed as `refinement` — same customer request, 100–1000× price difference, both compliant. (2) Act granularity: the search team (FR-034) bills one `cached_read` per *request*; the corpus team bills one per *entity served* — a 50-hit search costs 1 unit or 50 units depending on which team's endpoint an agent hits. Version-history reads (FR-020), the global change feed (FR-024), and a stale-entity read that triggers a refresh (one act or two, and which type?) all replay the same ambiguity.
- **Spine text that permits both:** AD-11: "Every billable act — `cached_read` and `refinement`, the PRD's two distinct units — is one row … written by `core/metering` alone." It fixes the two unit types and the single writer, but "billable act" is undefined, and classification is supplied by whichever caller invokes `core/metering` — the AD never says who decides, so two callers can classify the same serve differently.
- **Tightening:** Extend AD-11: classification is computed by **one function in `core/metering`** from a declared serve descriptor (source: KV/D1 = `cached_read`; live fetch+extraction = `refinement`); callers report facts, never unit types. Define act granularity in the same clause (e.g., one act = one delivered entity payload; list/search responses = one `cached_read` per request up to N entities, with N in pricing config; a cache-miss-triggered refresh on a read = one `refinement`, never both). Every serving endpoint names its serve descriptor in its route definition.

### C4. The wallet has no owning module, no balance representation, no debit rule — and two capability-map owners

- **Units:** agent rails (402/x402/wallet enforcement) × metering (billable-on-success), with Stripe quotas as a third party via FR-067.
- **Incompatible-but-compliant builds:** Build A (agent-rails team): wallet balance is a mutable micro-USD column in D1, **debited pre-serve** (reserve/hold) so an unfunded request can be 402'd cheaply and two concurrent requests can't overdraw; a failed run credits the hold back. Build B (metering team): the wallet is a *derived projection of the ledger* (balance = topup events − billable rows − compensating events), debit *is* the `usage_events` append post-delivery, and pre-serve there is only a read. These are incompatible money-state models: A double-counts once B's ledger row lands unless integrated by design; B allows negative balances under concurrency (two 5-second refinements both pass the balance read); the kill-switch (FR-064 "nothing is billed to a revoked token after the kill") collides with AD-11 ("a billable row exists only for a successfully delivered result") for a run in flight when the kill lands — A settles from the pre-kill hold, B refuses the post-kill append, both readings compliant. FR-067 additionally has *paid-plan API keys* drawing a wallet on quota exhaustion, while the ERD says only `AGENT_TOKEN }o--|| WALLET : draws` — so the two teams don't even agree on who may debit.
- **Spine text that permits both:** The capability map names two owners: "Agent rails (402, wallets, x402) | `core/metering`, `core/identity`" — no single module owns WALLET. AD-11 governs `usage_events` only and never mentions wallet balance mechanics. The Money convention pins units ("Ledger, pricing config, wallets: integer micro-USD"), not mechanics. Telling detail: the ID convention enumerates `ws_, usr_, key_, agt_, sch_, pipe_, run_, ent_, diff_, evt_, lst_, whk_, dlv_` — **there is no wallet prefix**; the entity exists in the ERD but not in the ID scheme.
- **Tightening:** New AD: WALLET is owned by exactly one module (recommend `core/metering`, since balance is money state). Balance is authoritative-D1 with a **reserve → settle/release** protocol: serve path places a hold (single D1 `batch()`), delivery settles the hold and appends the billable row in the same batch, failure/kill releases it; kill-switch semantics defined as "holds placed before the kill settle; no new holds after." Name who may draw (agent tokens; workspace keys only via the FR-067 top-up path — or explicitly reject FR-067's wallet reading). Add `wal_` (and `qsn_`/`exp_` while at it) to the ID table.

### C5. Nothing says who may write platform-corpus rows — on-demand refinement of a tracked entity creates two owners of one entity

- **Units:** corpus/verticals (scheduled platform pipelines) × universal on-demand refinement (FR-014).
- **Incompatible-but-compliant builds:** Tenant B on-demand-refines a URL that is already a platform tracked entity in the live dev vertical (the launch persona's most likely act: "refine this SDK changelog fresh"). Build A (on-demand team): dedupe against the corpus — write the fresh result as a new version of the platform entity at `platform` scope (everyone benefits, cache economics improve). Build B (corpus team): platform rows are written only by platform pipeline runs with their provenance chain; B's on-demand result is stored under `ws_B`. Under Build A, a tenant-paid, tenant-triggered write mutates the shared public corpus — potentially firing FR-022 webhooks to *other* workspaces' subscriptions and entering FR-020 version history off-schedule; under Build B the same URL accumulates a second, diverging version lineage per workspace. Same entity, two owners, two version histories — the exact defect class AD-6 exists to prevent, on its write side.
- **Spine text that permits both:** AD-6 is read-scoped: "**every read is owner-scoped**", "there is no unscoped read *API* to call", and it classifies only "custom-schema refinement output" as tenant-owned — refinement of a platform entity against the platform's own template schema is neither addressed nor assigned. No AD states write authority over `platform`-owned rows.
- **Tightening:** Extend AD-6 (or add AD-6b): `platform`-scoped rows are written **only** by platform-owned pipeline runs executing in `core/corpus`; tenant-triggered refinement output is always tenant-owned regardless of schema provenance; an on-demand request whose URL+schema matches a live platform entity within its freshness window is *served from* the platform corpus as a `cached_read` (never re-refined into it, never forked into a tenant lineage unless the tenant explicitly tracks it). Repository write methods take the same owner-scope parameter reads do.

### C6. x402 money order is self-contradictory: settlement is declared "a read of the ledger," but the auto-credit clause and the pinned middleware both imply pay-first

- **Units:** adapters/x402 + entry middleware × core/metering.
- **Incompatible-but-compliant builds:** Build A (rails team, following `x402-hono` 1.2.0 as shipped): the middleware verifies **and settles** payment pre-handler — money moves before the 5–15s refinement runs; on strict-validation failure the team must now refund an *anonymous* on-chain payer (AD-11's "auto-credit event" has no wallet to land in — the PRD says "refunded or never settled," but no module owns the refund transfer). Build B (metering team, following AD-11's letter): the middleware only *verifies* the payment authorization; the handler serves; `core/metering` appends the billable row; settlement then executes as "a read of this ledger" — money moves only for delivered results, and failures simply never settle. A's ledger contains payment-moved-then-credited pairs for every failure; B's contains none; reconciliation, refund tooling, and the FR-062 agent purchase path are built differently and cannot be merged without rework. Both teams can quote AD-11 at each other.
- **Spine text that permits both:** AD-11 in one sentence: "x402 settlement … [is a] *read* of this ledger" (serve-then-settle), and in another: "failed runs produce no billable row **(or an explicit auto-credit event where payment already moved)**" (pay-then-serve acknowledged). The Stack table pins `x402-hono 1.2.0`, whose default flow is pre-handler settlement. Nothing assigns the anonymous-refund path to any module.
- **Tightening:** Extend AD-11 (or add an x402 clause to AD-7/AD-11): pin one order — recommend verify-authorize pre-serve, settle post-delivery from the ledger row, never-settle on failure (making the PRD's "refunded or never settled" default to *never settled*, which eliminates the anonymous-refund machinery); where the facilitator forces settlement upfront, the compensating refund is owned by `adapters/x402`, triggered only by a metering compensating event. State explicitly that the `x402-hono` middleware is used in verify-only mode if that's the choice.

## HIGH findings

### H1. "AD-8-equivalent tool schemas" is a table annotation, not a rule — MCP and REST shapes for the same operation can drift freely

- **Units:** entry/mcp (Agents SDK tools) × entry/http (zod-openapi routes).
- **Incompatible-but-compliant builds:** The REST team defines refine/query/search request-response shapes as zod-openapi schemas; the MCP team hand-authors tool input/output schemas for the same operations (the Agents SDK accepts anything JSON-Schema-shaped). Field names, pagination envelopes, provenance blocks, and token-economics fields (FR-005) drift — an agent using the MCP tool and an SDK using REST see two different shapes for one operation, and FR-042's per-custom-schema tool is provisioned by a code path with no relation to the REST projection of the same schema.
- **Spine text that permits both:** AD-8 binds "Every **REST route**…" only; MCP appears solely in the capability map as "governed by AD-7, **AD-8-equivalent tool schemas**, AD-11" — a phrase with no rule body anywhere in the spine. The conventions pin shared enums ("imported by API, MCP, badges, and Studio") and AD-10 pins the error envelope across "HTTP/JSON-RPC," which proves the spine knows this seam exists — and covers only enums and errors.
- **Tightening:** Promote to a real clause in AD-8: every MCP tool's input/output schema is **derived from the same Zod source objects** as the corresponding REST operation (one schema module per operation in `packages/schema`/route defs; the MCP layer converts, never redefines). A tool whose shape is not generated from a REST-shared schema is a defect. FR-042 provisioning generates both projections from the stored custom-schema document (ties C1).

### H2. The human-session and OAuth principals are unmapped in the metering attribution model — and session transport on `/api/v1` is unpinned

- **Units:** Studio (pure public-API client) + MCP OAuth connections × metering/quotas.
- **Incompatible-but-compliant builds:** (1) Transport: the REST team builds `/api/v1` accepting only `Authorization: Bearer` keys/tokens (the only transport the conventions name) and expects Studio to obtain a key; the Studio team ships cookie-session fetches against the same routes (AD-7 gives humans sessions; AD-8 only demands Studio use public endpoints). Neither can integrate without an auth-middleware rework. (2) Attribution: AD-11 attributes "by principal (workspace/key/agent-token, or x402 payment reference)" — a Studio session or a user-delegated MCP OAuth grant is none of these. FR-032 demands MCP calls be metered "identically," so the MCP team invents an attribution (the OAuth grant's workspace? which one, for a user in three workspaces?), while the billing team's reconciliation and quota math only handle the enumerated principals. Whether a human browsing entity history in Studio (FR-044) burns `cached_read` quota is also decidable either way — the playground explicitly bills (FR-112), FR-044 says nothing.
- **Spine text that permits both:** AD-7: "Exactly four principal types…" (sessions exist but aren't wired to metering); AD-11's principal list quoted above; Auth-transport convention: "`Authorization: Bearer <credential>` **for keys and agent tokens**" — silent on sessions; AD-8: Studio "consume[s] types generated from that document" — silent on how it authenticates.
- **Tightening:** Extend AD-7/AD-11 jointly: sessions and OAuth grants resolve, at the route boundary, to a **workspace-scoped principal record** (grant pinned to exactly one workspace at consent time) that is a first-class attribution value in `usage_events`; pin the transport (e.g., session cookie accepted on `/api/v1` for the human principal, same router, one auth middleware resolving all four principals — no parallel Studio routes); enumerate which read surfaces are quota-bearing for human sessions (recommend: playground and API-equivalent reads bill; Studio management/browsing reads don't, listed explicitly).

### H3. Filter↔Workflow-step mapping is declared "orchestration" and therefore unpinned — retry semantics and inter-filter payload shapes can diverge per team

- **Units:** refinement core (filter chain) × pipelines/Workflows (scheduled execution) — and any two pipeline authors.
- **Incompatible-but-compliant builds:** Build A maps one filter = one Workflow step (memlog's intent); fetch's output exceeds Workflows' 1 MiB step-result limit on real pages, so filters must exchange **R2 keys**, changing every filter's I/O signature — and the sync on-demand path then either adopts R2-key passing (extra writes per request) or keeps in-memory buffers, giving two filter signatures for "the same filters." Build B bundles fetch+sanitize+extract into one step to stay under limits and minimize step billing; a transient failure after extraction now **re-runs the LLM call** on retry (double token cost, recorded twice per the LLM-usage convention), and if store+notify share a step, a retry after partial store double-notifies. Both builds are "the same filters, different orchestration."
- **Spine text that permits both:** AD-3: "entry modes may differ **only in orchestration**, never in filter behavior" — step boundaries, payload passing, and retry granularity are all orchestration. AD-4 pins "per-step durability/retry" without pinning what a step is. FR-004's fallback-model attempt is placeable inside the extract filter (sync team) or as step-level retry policy (workflow team) — divergent billing and behavior, both compliant.
- **Tightening:** Extend AD-3: the filter↔step mapping is part of the spine — one filter = one step, except a named allowed fusion list; filter I/O is defined as **references (R2 keys / D1 ids), never inline payloads**, identically in both modes; every filter's output write is idempotent on (run_id, filter) so any step retries safely; model fallback lives inside the extract filter in both modes; notify is always its own step/enqueue after store commits.

### H4. On-demand refinement has no run record in the model — but AD-9's quarantine requires one on every path

- **Units:** on-demand refinement (HTTP/MCP) × pipelines/ops (run bookkeeping, quarantine, provenance).
- **Incompatible-but-compliant builds:** The ERD derives runs from pipelines ("PIPELINE ||--o{ REFINEMENT_RUN : schedules") and quarantines from runs ("REFINEMENT_RUN ||--o{ QUARANTINED_SNAPSHOT"). The on-demand team, modeling faithfully, returns results/errors without creating REFINEMENT_RUN rows (no pipeline exists to hang one on) — and then has nowhere to put AD-9's mandatory quarantine ("R2 + run record") or FR-003 provenance, so invents a parallel record type. The pipelines team builds quarantine-inspection, drift monitoring (NFR-042), and the ops console against REFINEMENT_RUN only. Two bookkeeping models for one physical process; who executes the quarantine write (the validate filter that failed, a store filter that still runs on failure, or a catch handler in entry) is also unassigned, so sync and workflow modes can write it from different layers with different contents.
- **Spine text that permits both:** AD-9: "the raw snapshot is quarantined (R2 + run record)" — presumes a run record the ERD only grants to scheduled pipelines; AD-3 makes both modes "the same filters" but the run *entity* is never declared mode-independent.
- **Tightening:** Extend AD-3/ERD: **every** refinement execution — both entry modes — creates exactly one REFINEMENT_RUN (`run_` id; `pipeline_id` nullable, principal attribution mandatory); quarantine writes are performed by the shared chain's failure path (one function in `core/refinement`), never by entry layers; provenance (FR-003), quarantine, drift metrics, and billing all key off `run_id` in both modes.

### H5. Webhook fan-out has two plausible owners and no queue-message contract

- **Units:** refinement core (the chain's `notify` filter) × notify/webhooks (queue consumer, delivery records).
- **Incompatible-but-compliant builds:** Build A: the notify filter evaluates FR-022 subscription filters at diff time, writes N WEBHOOK_DELIVERY rows, and enqueues N per-delivery messages — the consumer just POSTs and retries. Build B: the filter emits one domain-event message; the consumer owns matching, fan-out, and delivery-row creation at dequeue time. The queue message shape (per-delivery vs per-event), the WEBHOOK_DELIVERY writer, and the filter-evaluation moment (a subscription created between diff and dispatch gets the event in B, misses it in A) all differ; producer and consumer built by different teams to different readings simply don't connect.
- **Spine text that permits both:** AD-4: "Outbound webhooks go exclusively through `refinery-webhooks` with per-delivery records, bounded retries, and a DLQ" — mandates the artifacts, not who creates them or what rides the queue. AD-3 puts `notify` in the shared chain; the capability map puts webhooks in `core/notify` — both own "notification."
- **Tightening:** Extend AD-4: the chain's notify filter does exactly one thing — publish a typed domain event (schema in `packages/schema`, carrying `requestId` per the logging convention) onto `refinery-webhooks`; `core/notify` (invoked by the consumer) owns subscription matching, fan-out, WEBHOOK_DELIVERY creation, signing, and retries. Filter evaluation happens at dequeue. One sentence kills the seam.

### H6. Whether the billable write may be deferred on the hot read path is decidable both ways — the `waitUntil` fence lives inside AD-4

- **Units:** corpus cached-read serving (NFR-001 edge latency) × metering/quotas.
- **Incompatible-but-compliant builds:** Every cached read must produce a D1 `usage_events` row (AD-11). Build A writes it synchronously in-request — D1 append becomes the latency floor of the "low-latency edge" read and its throughput ceiling. Build B defers it via `waitUntil` — reading the fence as scoped to AD-4's async substrate (its sentence begins "Cron never executes work inline; `waitUntil` is for telemetry only…"), and/or reasoning that the *caller* doesn't depend on the billing write. Build B drops billable events on eviction/crash (revenue loss, quota undercount); A and B also give quota enforcement (a "read of this ledger") different freshness. Two serving endpoints built by two teams will disagree on whether money writes may lag.
- **Spine text that permits both:** the only `waitUntil` fence in the spine sits inside AD-4's rule (binds "pipelines, webhooks, cron, refinement" — not the HTTP cached-read path) and is scoped by "never for writes **a caller** depends on" — billing is a write the *platform*, not the caller, depends on.
- **Tightening:** Move the `waitUntil` fence to the conventions table as global, and extend AD-11: the `usage_events` append is part of the serve transaction — a result is "successfully delivered" only after its row is durably written (same `batch()` where other writes occur); `waitUntil` may never carry ledger, wallet, or audit writes anywhere in the worker.

### H7. Export is bound to AD-6/AD-8 only — the capability map itself re-opens the unmetered-surface bug class AD-11 exists to close

- **Units:** fine-tuning export (FR-090) × metering + marketplace accrual.
- **Incompatible-but-compliant builds:** The export team ships JSONL/Llama3/Alpaca/RAG export "gated by the workspace's entitlements" with zero `usage_events` rows — fully compliant with its capability-map row, which lists only AD-6 and AD-8. The metering team's cost model (NFR-050), quota math, and the marketplace team's per-query creator share assume every corpus serve is ledgered. A workspace can then install a priced marketplace feed and bulk-export the entire slice: thousands of entity serves, zero `cached_read` rows, zero creator attribution — the economic replay of the prototype's unmetered `/mcp`, shipped by the book.
- **Spine text that permits both:** Capability map: "Fine-tuning export | `entry/http` export routes over `core/corpus` | **AD-6, AD-8**" — AD-11 absent; AD-11's Binds list ("billing, quotas, 402, Stripe, x402, marketplace attribution, audit stream, public metrics") never names export, and "every billable act" begs C3's question of whether an export is one.
- **Tightening:** Add AD-11 to the export row and settle the unit question in AD-11's act-definition clause (per C3): an export is N `cached_read` acts (or a distinct `export` unit type if pricing wants one — but pick now), attributed and creator-shared like any serve; entitlement gating controls *access*, the ledger still records *usage*.

### H8. The marketplace read-grant has no mechanism — and AD-6's owner-scope parameter is caller-asserted

- **Units:** marketplace (listings/installs) × corpus (owner-scoped repositories).
- **Incompatible-but-compliant builds:** Workspace B reads data from workspace A's listed feed. Build A (marketplace team): resolve the listing/install, then call the corpus repository **with A's `workspace_id` as the scope** — which "takes an owner scope parameter" verbatim, and quietly establishes that any module may assert any scope, reducing AD-6's guarantee to a calling convention one bug away from cross-tenant leakage. Build B (corpus team): repositories accept only the *requesting* principal's scope and perform the grant join themselves — requiring corpus to know marketplace's tables, and rejecting marketplace's Build-A calls outright. Different repository signatures, different enforcement points, both compliant; and if both ship defensively, grant checks run twice with two definitions of "granted" (is an install required, or does a public listing suffice? — FR-080 "browse and install" vs AD-6 "explicit marketplace listing" differ here too).
- **Spine text that permits both:** AD-6: "it becomes readable to others only through an explicit marketplace listing" (no mechanism) and "Every repository method takes an owner scope parameter" (no rule on who may assert which scope).
- **Tightening:** Extend AD-6: owner scope is a **sealed type constructed only by `core/tenancy`** from the authenticated principal — modules cannot fabricate a foreign scope; cross-workspace reads use a distinct `GrantScope{requester, grantor, lst_ref}` issued by `core/marketplace` (single grant-check implementation: install required or not — decide) and honored by corpus repositories, which record the `lst_` ref into the serve descriptor (feeds C2's attribution field).

## MEDIUM findings

### M1. Quota enforcement mechanism: ledger-read vs Rate Limiting binding vs derived counter

- **Units:** Stripe quotas × agent rails 402.
- **Both compliant:** AD-11 says "Quotas … are reads of this ledger," but a per-request `SUM` over `usage_events` is unworkable on the hot path, while the conventions row "Rate limiting: Workers Rate Limiting binding. Never KV counters" invites one team to implement *monthly quota* on the binding (approximate, non-ledger) while another builds a KV-cached ledger projection (allowed as an AD-12 derived projection — colliding with "never KV counters" if read as global). Different teams will 402 at different counts.
- **Tightening:** One sentence in AD-11: quota checks read a **ledger-derived counter projection** (KV or D1 aggregate, rebuildable per AD-12; the "never KV counters" fence applies to rate limiting only) with a stated max staleness; the ledger remains the truth at invoice time.

### M2. Derived-projection writes (KV/Vectorize): which unit writes them, and does failure fail the serve?

- **Units:** refinement store filter × corpus/search indexing.
- **Both compliant:** AD-12 pins order ("written after D1 commit") but not the writer or failure semantics. The store filter can write embeddings inline (adds model-call latency to every sync refine) or hand off to indexing in `core/corpus` (needs a queue/step the spine doesn't name); one team fails the run on Vectorize errors, the other treats projections as best-effort-rebuildable. Search visibility of fresh results then differs by entry mode.
- **Tightening:** One clause in AD-12: projection writes are owned by the store filter's post-commit hook in both modes, are best-effort (failure never fails a committed run) and self-healing (a rebuild path exists and is the recovery mechanism the AD already promises).

### M3. Global change feed (FR-024) scope composition

- **Units:** change-feed endpoint × corpus repositories.
- **Both compliant:** AD-6 repositories take *an* owner scope; the authenticated global feed is naturally a union (platform corpus + the caller's workspace entities). One team ships platform-only; another ships the union via two queries; a third adds marketplace-granted entities. Different customers see different products, all owner-scoped.
- **Tightening:** Define the feed's scope set once (recommend: platform + caller's workspace + active grants) as a named composite read in `core/corpus`, reusing H8's scope types.
