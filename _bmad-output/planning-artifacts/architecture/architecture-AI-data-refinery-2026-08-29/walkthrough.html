01 · Condition report

Where we stand

We audited every line of the prototype. The honest verdict: it proves the product runs on Cloudflare; almost nothing else survives contact with real customers.

That's not a criticism of the idea — it's what an AI-generated prototype is for. But it means the architecture work wasn't "harden what exists." It was "decide how the real thing is built." Here is what the audit confirmed, with the code as evidence:

Confirmed

No engine behind the scheduler

The cron job selects pipelines, logs a count, and throws them away. Refinement only ever runs inside a live HTTP request. There is no queue, no background execution of any kind.

Confirmed

Auth is unsalvageable

Founder passcodes hardcoded in source, in the database, and in the frontend — and any paying customer's API key is accepted as a platform admin credential.

Confirmed

Tenant isolation doesn't exist

Core data tables have no tenant column at all. Anyone can list every workspace and join any of them, unauthenticated.

Gap

Two launch commitments, zero code

Agent payments (x402) exist only as a roadmap bullet. The MCP server is hand-rolled on an obsolete 2024 protocol with no auth and no metering.

Gap

Nothing is verified

Seven unit tests, no CI, no staging environment, and dashboard numbers ("99.998% uptime") that are hardcoded string literals.

Full evidence with file-and-line citations lives in code-sweep.md alongside the spine.

02 · Platform

The anchor decision: Cloudflare, ratified

You chose Cloudflare; the audit says the choice holds. Since the internals need rebuilding on any platform, the only question that mattered was whether Cloudflare fits this product — and it does, inside three fences.

What we gain
  • Near-zero ops for a two-person team — no servers, no Kubernetes, no 3 a.m. pager
  • Everything the product needs is a native primitive: SQL, object storage, queues, durable workflows, vector search, edge inference
  • The 402/agent-payments story is edge-native — Cloudflare co-founded the x402 standard we're building on
What we fence
  • Workers CPU ceilings: the pipeline is designed around them (verified: up to 5 min per invocation, paid plan)
  • D1's 10 GB per-database cap: a tripwire fires at 5 GB, with shard/archive options already named
  • Model quality: extraction may outgrow Workers AI, so external models are allowed — but only through Cloudflare's AI Gateway, keeping cost tracking on-platform

Every escape hatch is written into the contract as a tripwire, not a vibe: splitting into multiple services requires a measured platform limit, documented, before anyone gets to do it.

03 · Paradigm

The shape: one deployable, three layers

A hexagonal modular monolith: one worker to deploy and reason about, with hard internal walls a reviewer — or a linter — can enforce mechanically.

Why this shape, for us specifically: development stays AI-assisted, and AI-generated code drifts unless the rules are checkable without judgment. Every wall above is a grep or an import-graph check — "no SQL in entry/", "no Cloudflare types in core/" — so review catches violations mechanically instead of relying on vigilance. The prototype's worst bugs were all wall violations of exactly this kind.

Studio (the dashboard) is a pure client of the public API. It gets no private endpoints, ever — so anything the dashboard can do, a customer's own code can do, and the API can never silently rot.

04 · Execution

One pipeline, two ways in

Refinement is a fixed seven-stage chain. An API call runs it live in the request; the scheduler runs the identical chain as a durable workflow. There is no third path, and the two can never drift apart.

The decisions inside this picture

Durable workflows, not a hand-rolled scheduler. Each scheduled run is a Cloudflare Workflow instance: if the site times out at stage two, only stage two retries — we don't re-pay for the model call that already succeeded. The verified current limits comfortably cover launch scale (50,000 concurrent runs; ~80,000 runs/month inside the free step allowance).

Everything assumes retries happen. Queues deliver at least once, so every step is idempotent by construction — a redelivered message can't spawn a duplicate run, double-bill a query, or fire a webhook twice. The run ID is the workflow ID; creating it twice is a no-op.

The prototype's worst habit is banned by name. When the model returned garbage, the old code invented a fallback object and served it as if real. The contract now reads: a schema failure fails the run, quarantines the raw page, and bills nothing.

05 · Tenancy

Who owns what

Every row in the system lives in exactly one place: the platform's shared corpus, or one customer workspace. There is no third state, and no code path that reads without saying whose data it wants.

Platform corpus

Refined once, served to everyone

The public verticals are the unit-economics engine: written only by platform pipeline runs; a customer request can read them cheaply but never mutate them.

Workspace-owned

Private by default

A customer's custom schema is their IP, so everything it produces is their data. It becomes visible to others only through an explicit marketplace listing they create.

Isolation is enforced by construction, not by discipline. The prototype's worst leak was trusting a workspace ID sent by the client. Now the "whose data" value is a sealed type that only the tenancy module can mint from a verified login, key, or payment — request data physically cannot become a scope. A feature developer cannot write the leak, because the type system won't let the value exist.

Cross-tenant reads exist in exactly three sanctioned forms — a marketplace grant (after entitlement check), an audited admin scope, and search unions over platform + own + granted data. Anything else has no API to call.

06 · Billing

Money: one ledger, two rails

Humans subscribe through Stripe; agents pay per query through x402 wallets or drive-by micropayments. Every unit of value — both rails, all four principal types (human, API key, agent token, drive-by payer) — lands as one row in one append-only ledger.

The adversarial review attacked this layer hardest, and the contract now makes four failure modes structurally impossible:

No double-spend

Wallet debits are hold → settle/release in one atomic batch. A hundred concurrent agent calls against a one-query balance can't overdraw — the predicate and the write commit together.

No replayed payments

An x402 payment proof is single-use (uniqueness enforced in the ledger); a redelivered Stripe webhook is deduplicated by event ID. Replays grant nothing.

No revisionist billing

Prices are frozen into the row at serve time. Refunds and credits are new compensating rows from three named authorities — history is never edited.

No anonymous-refund machinery

Drive-by x402 runs verify payment first but settle only after delivery. A failed run is simply never settled — so we never owe an anonymous wallet a refund.

You'll ask "billed as cached or billed as fresh?" — so did the reviewers. One function in the metering module classifies every serve from the facts (cache-fresh vs. live extraction); feature code reports facts and can never pick its own price.

07 · Security posture

Every prototype flaw, answered structurally

"Proper engineering and audit" was the whole engagement. The contract answers each shipped flaw with a rule that makes the flaw unwritable — not a patch, a wall.

The prototype shippedThe contract's answer
Hardcoded founder passcodesAdmin is a role on named accounts, second factor required, granted only by another admin, bootstrapped by runbook — passcodes cease to exist
Any Pro key = platform adminAdmin surfaces accept founder Studio sessions only; no key or token of any kind reaches them
Client-supplied workspace IDs trustedScopes are sealed values only the tenancy module can mint from a verified principal
Unauthenticated, unmetered MCPMCP resolves through the same auth and the same ledger as REST — a tool call can never do what its REST twin would deny
Webhooks as an SSRF holeAll outbound URLs — fetches and deliveries — pass one SSRF policy, re-validated after DNS resolution
Prompt injection unconsideredWeb content is tainted forever: re-fenced on every model call, never allowed to steer a fetch or a write, rendered inert in badges and UI
Audit tables read but never writtenAuth, billing, admin, and denial events are append-only rows nothing can edit — the SOC 2 evidence trail starts on day one

08 · Reference

The sixteen rules

The full contract, one card per decision. Each one names the divergence it prevents — expand what you want to interrogate; the spine file carries the binding wording. The three cards marked countersign back the calls waiting for you in section 09.

AD-1Platform is Cloudflare countersign▶

Prevents: infra sprawl a two-person team can't operate.

All compute and state on Cloudflare primitives. External model providers only via AI Gateway; anything else moving off-platform is a contract change.

AD-2One deployable API worker▶

Prevents: premature microservices.

Single worker, three layers with lintable walls. A second service requires a measured platform limit, on record.

AD-3One refinement core, one run record▶

Prevents: sync and scheduled paths drifting apart.

One filter chain; one filter = one workflow step; every execution — either mode — creates exactly one run record that billing, provenance, and quarantine all key off.

AD-4Workflows execute, Queues dispatch, all idempotent▶

Prevents: duplicate runs, double billing, double webhooks, silent webhook death.

Retries are assumed everywhere. Deliveries are signed, recorded, retried, and visibly paused on exhaustion — never dropped.

AD-5Drizzle owns the schema▶

Prevents: the split-brain schema bug that already shipped.

Tables defined once in TypeScript; migrations, row types, and validators are all generated from it. Hand-written DDL is a defect.

AD-6Two data classes; scopes are minted, never asserted countersign▶

Prevents: cross-tenant leaks; two owners of one entity.

Platform corpus vs. workspace resources; sealed scope values from the tenancy module; three sanctioned cross-tenant read forms; platform rows written only by platform runs.

AD-7Four principals, one auth middleware▶

Prevents: parallel auth schemes; cached credentials outliving revocation.

Human, API key, agent token, drive-by payer — one resolver. Authorization state read fresh per request; kill-switch binds at the next call. Admin = MFA'd role.

AD-8One schema source per operation▶

Prevents: MCP tools and REST drifting into different shapes for the same operation.

Route definitions generate validation, types, and the OpenAPI doc; MCP tool schemas derive from the same source; Studio and SDKs consume the contract.

AD-9Validate both boundaries; failure fails the run▶

Prevents: the synthesized-fallback habit; unvalidated inbound JSON.

Every request validated at the edge; model output passes the schema or the run fails and quarantines. No guesses served, ever.

AD-10One error envelope▶

Prevents: internal errors leaking; per-route error dialects.

One shape, one taxonomy, one place that maps domain errors to the wire.

AD-11The append-only ledger▶

Prevents: unmetered surfaces; revisionist money; payment replay.

One writer, a fixed row contract with prices frozen at serve, delivery-synchronous appends, single-use payment evidence, compensating events from three authorities only. Audit events follow the same pattern.

AD-12D1 is truth; caches are projections; R2 holds raw▶

Prevents: multi-store writes with no source of truth; takedowns that keep serving.

Caches and vectors are rebuildable; raw snapshots owner-scoped with bounded retention; an opt-out purges storage, not just fetching.

AD-13Three environments, config through bindings▶

Prevents: hardcoded URLs and price IDs; testing in production.

Local, staging, production; CI gates every merge; promotion is a manual, deliberate act.

AD-14One policed fetch boundary; taint is forever▶

Prevents: SSRF; disrespectful crawling; injected content steering the system.

One fetch port enforcing SSRF policy, robots.txt, identifiable UA, pacing, and the opt-out registry. Web content stays fenced on every later model call and inert in every rendering.

AD-15One wallet owner; verify, serve, then settle countersign▶

Prevents: double-spend; anonymous-refund machinery; kill-switch ambiguity.

Metering owns the wallet; debits are atomic hold→settle/release; x402 verifies before serving and settles only after delivery — failures never settle.

AD-16One custom-schema format, one compiler▶

Prevents: the same schema validating differently on different surfaces — flipping what gets served and billed.

A constrained JSON Schema profile, checked at publish; one compiler emits the runtime validator, the MCP tool shape, and the OpenAPI components.

09 · Countersign

Your four calls & what's next

Everything in this deck is decided and defensible — but these four decisions shape the product enough that you should own them too. Disagree with any of them, and now is the cheap moment to say so.

  1. Cloudflare, ratified. We double down on the platform rather than hedging across clouds — betting that near-zero ops matters more to a two-person company than portability. Binding rule: AD-1.
  2. Customer refinements are private by default. A customer's custom-schema output is their data; it enters the shared economy only when they list it. We trade some of the corpus-growth flywheel for a clean IP story. Binding rule: AD-6.
  3. Drive-by agent payments settle only after delivery. Failed runs are simply never settled — so there is nothing to refund — which kills a whole class of anonymous-refund machinery, at the cost of slightly later revenue recognition. Binding rule: AD-15.
  4. Marketplace pays by visible accrual at launch; live payouts fast-follow. The reviewers found the fraud loop in launch-day payouts (chargeback + instant payout = free money); shipping accrual first closes it, with payouts following in Phase 3. Lives in the deferral register below, not the rules.

Deliberately postponed — with tripwires

A good contract also says what it won't decide yet. Each deferral carries the condition that reopens it, so nothing is postponed into oblivion.

  • x402 facilitator & chainPhase 0 integration spike — the protocol and settle order are committed; the vendor is not
  • Pricing numbersPhase 0 exercise, using real telemetry unit costs — the units and row contract are already fixed
  • Creator payouts (Stripe Connect)First Phase 3 fast-follow; visible ledger accrual is the launch mechanism
  • D1 growth strategyTripwire at 5 GB — half the platform cap
  • Splitting the workerOnly on a measured platform limit, documented
  • Snapshot retention & deletion workflowBefore any corpus reaches the marketplace, or the first takedown — whichever is first
  • Audit tamper-evidence beyond D1At SOC 2 readiness work, or the first enterprise contract
  • Extension, CLI, and frontend toolchain upgradesPost-launch; all bound by the same API contract when they arrive

What happens next

The spine becomes the standing companion to a machine-readable spec, which then breaks into epics and stories — every one of them citing the rule IDs above, so review always has a contract to point at. The pipeline core and the metering ledger are the natural first builds: everything else leans on those two.
